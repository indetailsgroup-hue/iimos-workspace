สถานะ: มติสถาปัตยกรรม Phase A ที่เจ้าของอนุมัติ โดยมีเงื่อนไขบังคับก่อน Phase B

อำนาจใช้งานจริง: ไม่มี
G−0: DISABLED
G−1: BLOCKED

1. มติ

MONOLITH จะจัดงานซ่อมอาคารและงานบำรุงรักษาสถานที่เป็น bounded context ใหม่ชื่อ Repair Operations ภายใน modular monolith เดิม ส่วน Repair Intelligence เป็นชั้นช่วยวิเคราะห์ภายใน context นี้ ไม่ใช่ระบบหลักของข้อมูล และไม่ใช่ runtime หรือ microservice แยกต่างหาก

ห้าม merge repository Repair Intelligence ที่แยกทดลองอยู่เข้ามาโดยตรง Repository ดังกล่าวให้คงไว้เป็นแหล่งหลักฐานการบ่มแนวคิดและ governance เท่านั้น กฎโดเมนและ records ที่ผ่านการอนุมัติอาจถูก port ภายหลังผ่าน adapter ที่ระบุชัด เมื่อผ่าน gate ใน ADR นี้แล้ว

ADR นี้ให้อำนาจเฉพาะการจัดทำเอกสารสถาปัตยกรรม ไม่ให้อำนาจสร้าง runtime code, database schema, LINE configuration, webhook routing, feature activation, การซ้อมมนุษย์, ติดต่อ vendor, ใช้เงิน หรือเปิดใช้งานจริง

2. บริบทและเจตนา

เป้าหมายเชิงปฏิบัติการคือให้พนักงานในอาคารแจ้งปัญหาได้ง่ายที่สุด—โดยปกติส่งรูปผ่าน LINE ของอาคาร—ขณะที่ MONOLITH ดูแลการรักษาหลักฐาน การส่งต่อ การประสานเคส การยกระดับความปลอดภัย การจัดหาราคา การอนุมัติ การตรวจรับ และ audit อยู่หลังบ้าน

MONOLITH มี platform capabilities แนวนอนอยู่แล้ว ได้แก่ การตรวจลายเซ็นและ idempotency ของ LINE webhook, identity binding, การจำกัดสิทธิ์ตาม site, capture artifacts, การดึง media, notification, รูปแบบ approval และ append-only audit การสร้างสิ่งเหล่านี้ซ้ำจะทำให้เกิด trust boundary ที่แข่งขันกันเอง

โมเดล installation_issues เดิมไม่สามารถเป็น aggregate ของ Repair Operations ได้ เพราะผูกกับโครงการติดตั้งและห้อง และมี lifecycle เฉพาะงานติดตั้ง กระบวนการ workflow เดิมก็ผูกกับลำดับ Sale ถึง Installation จึงห้ามบิดความหมายเพื่อแทนงานซ่อมอาคาร

4. ขอบเขตและความเป็นเจ้าของ

Repair Operations เป็นเจ้าของ lifecycle ของ repair case, safety containment, technical assessment, assignment, การประสาน sourcing, การเปรียบเทียบราคา, authority reference, การทำงาน, การตรวจสอบ, การตรวจรับ, warranty, การเปิดเคสซ้ำ และประวัติ case event

ส่วนที่ reuse จาก MONOLITH ผ่าน adapter ได้แก่:

  • การตรวจลายเซ็น LINE, channel topology, webhook idempotency และ outbound delivery;
  • identity binding และ actor resolution;
  • ขอบเขต site_code และแนวทาง row-level security;
  • capture artifacts และ media retrieval;
  • notification, retry, quiet hours และ escalation;
  • รูปแบบ immutable audit และ autonomy vocabulary กลาง

ส่วนที่ห้าม reuse หรือบิดความหมายโดยตรง:

  • ห้ามใช้ installation_issues เป็น facility repair case;
  • ห้ามใช้ process model ตั้งแต่ Sale ถึง Installation เป็น repair lifecycle;
  • ห้ามตีความ work-item approval เดิมเป็นอำนาจการเงินหรือกฎหมาย;
  • ห้ามใช้ generated G−0 forms เป็น runtime records

5. Conceptual flow

LINE webhook → ตรวจ context binding → fail-closed context router → repair intake draft → human triage → repair case → safety/assessment → sourcing/authority → work → inspection/acceptance → close หรือ reopen

รูป ข้อความ ผล classifier หรือ feature flag เพียงอย่างเดียวห้ามสร้างข้อผูกพันภายนอก วินิจฉัยภาวะอันตราย เลือก vendor อนุมัติค่าใช้จ่าย หรือปิดเคส

6. เงื่อนไขบังคับก่อน Phase B

6.1 Context routing ต้อง fail closed

Router ต้องใช้ controlled binding metadata เป็นหลัก ไม่ใช่ AI content classification และต้องคืน RESOLVED_INSTALLATION, RESOLVED_FACILITY_REPAIR, AMBIGUOUS_OR_CONFLICTING หรือ UNBOUND

กรณีกำกวม ขัดแย้ง หรือยังไม่ผูก ห้ามเข้า business lifecycle ต้องไป quarantine/triage queue ที่มนุษย์ควบคุม รักษาหลักฐานตาม privacy rule และไม่สร้าง side effect ด้าน completion, procurement, vendor notification หรือ authority

กรณีอาจมีอันตรายทำได้เพียงยก Human Safety Trigger ให้มนุษย์ตรวจเร่งด่วน ห้ามวินิจฉัยจากรูป “ไม่แน่ใจให้ยกระดับ” และห้าม route แบบเงียบ ๆ

6.2 ต้องกำหนด retention และ privacy แยกต่างหาก

ก่อนสร้าง facility_repair_evidence ต้องมี data inventory และ retention/privacy rule สำหรับรูป ตัวตนผู้ส่ง ตำแหน่ง asset reference annotation ผลจำแนก access log และ exported copy

ตราบใดที่ Legal Entity และ Data Controller เป็น UNDEFINED Preservation Hold มีผลเหนือ automatic deletion; cleanup worker ห้ามลบหลักฐาน; ห้าม cloud/cross-border extraction ที่ไม่อนุมัติ; ทุกการเข้าถึงและสำเนาต้องถูกควบคุมและบันทึก; การพบเอกสารที่เคยหายไม่ปลด hold อัตโนมัติ Phase B ถูกบล็อกจนมี retention schedule ที่อ้างฐานกฎหมายหรือสัญญาและผู้อนุมัติ

6.3 การเปิดใช้ต้องผูกกับ authority ไม่ใช่ feature flag อย่างเดียว

technical_flag = ON และ valid_G1_unblock_record = PRESENT และ authority_reference_matches = TRUE

G−1 Unblock Record ต้องได้รับความเห็นชอบเป็นเอกฉันท์จาก Corporate Authority Approver, Safety Owner, Privacy/Governance Approver และ Independent Readiness Observer ส่วน Custodian นักพัฒนา ผู้ดูแล repository, CI/CD, deployment operator และ database administrator ไม่มีอำนาจสร้าง activation ด้วย configuration

Authority evidence ที่ขาด หมดอายุ ถูกแทนที่ ขัดแย้ง นอกขอบเขต หรือจับคู่ไม่ได้ ต้อง fail closed ความเงียบ เวลาที่ผ่านไป deployment สำเร็จ หรือ environment variable ไม่เปิด route

6.4 Phase B ต้องถอดกลับได้และมี rollback

ตราบใดที่ไม่มี production data หรือ external commitment Phase B ต้องเป็น additive และถอดได้ โดยมี dependency inventory, empty-data teardown หรือ compensating migration ที่ทดสอบแล้ว, ไม่มีการแก้ domain เดิมแบบย้อนกลับไม่ได้, feature-off ไม่เปลี่ยน flow เดิม, orphan scan และ withdrawal audit record

ห้ามเขียนทับ migration history ที่ใช้แล้ว Shared หรือ production-like environment ต้องใช้ compensating migration ใหม่ ต้อง rollback เมื่อ drills ล้มเหลวซ้ำโดยไม่มี correction path, ไม่สามารถกำหนด legal/privacy authority, ตรวจ authority ไม่ได้, retention ไม่ผ่าน หรือ context boundary ผิดจากงานจริง

เมื่อมี production data หรือ external commitment ต้องใช้แผน archival, migration, notification และ legal closeout ที่อนุมัติแยก

7. ขอบเขตแต่ละระยะ

Phase A — Architecture Port (อนุญาต)

  • รักษา repository แยกและ provenance;
  • บันทึกมติ bounded context;
  • ระบุ platform reuse และ coupling ที่ห้ามทำ;
  • ไม่สร้าง runtime code, schema, route, flag, credential หรือ live configuration

Phase B — Skeleton Integration (ยังไม่อนุญาต)

วางแผนได้เมื่อเงื่อนไขทั้งสี่เป็น acceptance criteria ที่ทดสอบได้ และเจ้าของอนุมัติการวางแผนแยก

Phase C — G−0 Human Validation (ยังไม่อนุญาต)

Human drills 9 รายการยังไม่ถูกดำเนินการ Tests ทางเทคนิคไม่ทำให้ Gate ผ่าน

Phase D — Controlled G−1 (ถูกบล็อก)

ต้องมี Legal Entity, Data Controller, retention schedule, authority/DOA records, G−1 unblock แบบเอกฉันท์ และ cohort ที่อนุมัติ

Phase E — Automation Research (ถูกบล็อก)

AUTOMATION_RESEARCH_ELIGIBLE เป็นสิทธิ์ศึกษา ไม่ใช่อำนาจ deploy automation

8. ทางเลือกที่ปฏิเสธ

  1. Merge repository ตรง: แหล่งต้นทางเป็น governance/readiness prototype ไม่ใช่ runtime feature
  2. ขยาย installation_issues: aggregate, authorization, location และ lifecycle เป็นงานติดตั้งโดยเฉพาะ
  3. สร้าง microservice: สร้าง trust boundary ซ้ำก่อนพิสูจน์ความต้องการ scaling หรือ ownership
  4. ทำ workflow engine ให้ generic ก่อน: เร็วเกินไปและเสี่ยงทำให้ workflow เดิมอ่อนลง

9. ผลที่ตามมา

MONOLITH รักษา trust boundary กลางไว้หนึ่งชุด ขณะที่ repair semantics ชัด ทดสอบแยกได้ อยู่ภายใต้มนุษย์ และย้อนกลับได้ก่อน production ต้นทุนคือ lifecycle และ adapters เฉพาะ การทำ LINE binding ให้รู้ context และการคง financial approval ไว้ในสถานะบล็อกจนตรวจ legal authority และ DOA แล้ว Phase A ไม่สร้าง operational capability

10. เกณฑ์จบ Phase A

  • เงื่อนไขก่อน Phase B สี่ข้อชัดและไม่ขัดกัน;
