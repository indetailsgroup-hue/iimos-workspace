OR-8.1 — การจัดการ end-of-line ที่รากของ registry

วันที่: 30 กรกฎาคม 2026 กำกับ: 51c6428bf73fdeb41cc5faa5923f6143ad875633 คำถามที่เสนอต่อเจ้าของ: การ clone ใหม่บน Windows เขียน coverage-snapshot.json ที่ commit ไว้จาก LF เป็น CRLF ผู้อ่านจึงยืนยัน digest ที่เผยแพร่กับไฟล์ที่ได้รับ ไม่ได้ ควรตรึงการจัดการ end-of-line หรือไม่ และถ้าตรึง ขอบเขตแค่ไหน

คำตัดสิน: ตรึง ที่รากของ registry เท่านั้น ไม่ให้ renormalise ทั้ง repository ในการเปลี่ยนแปลงเดียวกัน

ผลที่บันทึกไว้: การตรึงเป็นราย glob (*.json -text, *.jsonl -text) ดังนั้น ไฟล์ภายในรากของ registry ที่ไม่ตรงกับ glob ใดเลย — .gitattributes, .gitignore — ยังคงถูกแปลงเมื่อ checkout ข้อนี้อยู่ในคำตัดสิน ไม่ใช่การเบี่ยงเบนจากคำตัดสิน

ยังเปิดอยู่ภายใต้คำตัดสินนี้: manifest baseline adoption ของงานที่ 1 เผยแพร่คู่ path กับ SHA-256 จำนวน 77 คู่ ซึ่งไม่มีคู่ใดทำซ้ำได้บน checkout ใหม่ ส่วนที่ว่า เรื่องนี้จะได้ wave ของตัวเองหรือไม่ ยังไม่ได้ตัดสิน

OR-8.2 — allowlist ชื่อไฟล์ที่ระบุชัดสำหรับ input ที่ไม่ใช่ item

วันที่: 30 กรกฎาคม 2026 กำกับ: 26d344e3edafb7a1e693c358087c001d51c0373b คำถามที่เสนอต่อเจ้าของ: งานที่ 9 จะสร้าง brand-universe.jsonl และ source-denominator.jsonl ที่รากของ registry และทั้งสองจะล้มแรง เพราะทุก *.jsonl ถูกอ่านเป็นข้อมูล item ควรเพิ่ม allowlist หรือไม่

คำตัดสิน: เพิ่ม พร้อมข้อบังคับสองข้อที่เจ้าของระบุไว้เป็นส่วนหนึ่งของตัวเลือกที่เลือก:

  1. allowlist ต้องเป็น ชื่อไฟล์ที่ระบุชัด ไม่ใช่ pattern กว้าง ๆ
  2. .jsonl ที่ไม่รู้จักต้อง ยังล้มดังเหมือนเดิม ไม่ใช่ถูกข้ามเงียบ

ผลที่บันทึกไว้: เพราะยังไม่มี type ของ brand record แถวที่ไม่ว่างใน brand-universe.jsonl จึงถูกปฏิเสธ แทนที่จะถูกเดารูปแบบให้ schema ของแถวนั้น เป็นของงานที่ 9 ที่จะนิยาม

ช่องว่างที่บันทึกไว้ ซึ่งคำตัดสินนี้ไม่ครอบคลุม: การรับประกันเรื่องการล้มดัง ๆ มีขอบเขตอยู่ที่นามสกุล .jsonl ไฟล์ที่รากของ registry ซึ่งไม่ใช่ *.jsonl — เช่น item object ที่ถูกต้องแต่เขียนเป็น items.json — จะถูกข้ามเงียบและไม่มีข้อความใดบอก

OR-9.1 — แหล่งข้อมูลที่ระบุชื่อแล้วแต่ยังไม่ได้ดึง ควรมีหน้าตาอย่างไร

วันที่: 31 กรกฎาคม 2026 กำกับ: งานที่ 9 ซึ่งยังไม่ได้ลงมือทำ คำถามที่เสนอต่อเจ้าของ: งานที่ 9 ประกาศ URL ต้นทางของ 12 แบรนด์ ซึ่ง ยังไม่มีใครไปดึงมาอ่าน แต่ทุก type ในโมดูลออกแบบมาสำหรับแหล่งที่อ่านและ hash แล้ว เสนอสามทางเลือก:

  • ก — ดึงและ hash จริงก่อน ที่ดึงไม่ได้กลายเป็น BLOCKED พร้อมเหตุผล ไม่แตะ

code แต่งานที่ 9 กลายเป็นงานที่ต้องใช้ network และ rights review

  • ข — เพิ่มสถานะที่สามซึ่งหมายถึง มีชื่อ ยังไม่ได้อ่าน ไม่นับใน

registered_source_count และมีวรรคที่นับได้ของตัวเองใน coverage_statement

  • ค — ประกาศทั้ง 12 เป็น BLOCKED เหตุผล "ยังไม่ได้ดึง" ไม่แตะ code

แนะนำว่าไม่ควรทำ เพราะ BLOCKED แปลว่า อ่านไม่ได้ ไม่ใช่ ยังไม่ได้ลอง และการใช้ซ้ำแบบนั้นคือรูปแบบการ relabel เพื่อให้ผ่าน gate ที่เจ้าของห้ามไว้

คำตัดสิน: ข

ข้อบังคับที่ส่งต่อไปยัง brief ของงานที่ 9: สถานะที่สามต้องไม่เงียบ coverage_statement ต้องเผยแพร่จำนวนแหล่งที่ประกาศแล้วแต่ยังไม่ได้อ่านออกมาเป็นคำ เพื่อไม่ให้ประโยคที่เผยแพร่ถูกอ่านว่าเป็น coverage สถานะที่สามที่เพียงถูกกันออกจาก จำนวน registered โดยไม่ถูกพูดออกมา คือการพองตัวเลขที่โมดูลนี้มีไว้เพื่อป้องกันพอดี
